# Drivers arquitectónicos

Los **drivers arquitectónicos** identificados para el sistema son los siguientes:

| ID   | Driver arquitectónico                                                                                        | Origen                                    | ¿Por qué influye en la arquitectura?                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| DA01 | Los datos de cada institución deben estar aislados aunque compartan la plataforma.                           | AC01 – Seguridad; RC15 – Multiinstitución | Define cómo se identifica la institución en cada petición y cómo se filtran los datos en la base de datos (RLS).                              |
| DA02 | Los módulos deben adecuarse al tipo de institución sin programar.                                            | AC02 – Adaptabilidad                      | Obliga a separar el motor genérico de la configuración (plantillas, funciones y etiquetas) y a que frontend y gateway lean esa configuración. |
| DA03 | El sistema debe soportar picos de matrícula, cierre de corte y emisión masiva de documentos.                 | AC03 – Escalabilidad                      | Influye en dividir el sistema en servicios que escalen por separado y en procesar los PDF de forma asíncrona.                                 |
| DA04 | La generación de PDF no debe bloquear al usuario ni a los demás servicios.                                   | AC04 – Rendimiento; RC04 – Workers Python | Lleva a una cola de trabajos (Kafka) y a workers independientes.                                                                              |
| DA05 | La caída de un módulo no crítico no debe detener los módulos críticos.                                       | AC05 – Disponibilidad                     | Influye en la separación por servicios, la comunicación por eventos y el aislamiento de fallas.                                               |
| DA06 | Los documentos firmados deben ser íntegros y verificables, y la firma debe hacerse con el agente Firma Perú. | AC06 – Integridad; RC11 – Firma Perú      | Condiciona el flujo de firma (en la computadora del firmante), el almacenamiento inmutable y la verificación pública.                         |
| DA07 | Cada servicio debe poder cambiarse y desplegarse sin afectar a los demás.                                    | AC07 – Mantenibilidad                     | Influye en la arquitectura hexagonal dentro de cada servicio y en contratos explícitos (API y eventos).                                       |
| DA08 | El sistema debe integrarse con varios proveedores externos y poder cambiarlos.                               | AC08 – Interoperabilidad                  | Lleva a aislar cada proveedor detrás de un puerto y un adaptador.                                                                             |
| DA09 | Las operaciones deben poder rastrearse entre servicios.                                                      | AC09 – Observabilidad                     | Requiere identificadores de correlación, trazas distribuidas y registros estructurados.                                                       |
| DA10 | El stack está definido: Next.js, Go, Python con uv, Kafka, Redis y PostgreSQL.                               | RC02 – RC07                               | Limita las alternativas tecnológicas de cada contenedor.                                                                                      |
